# 현재 구조와 운영 경계

[서비스 소개로 돌아가기](../README.md) · [개발 가이드](./development.md)

## 공개 서비스

홈 `/`에서 기본 캐릭터 레비를 소개하고 `/talk`로 대화를 시작합니다. 공개 UI는 선택지 중심이며, 직접 입력은 ‘다른 마음이 있어요’로 펼칩니다. 응답 모드·상담 스타일 선택은 제공하지 않고 서버 기본값 `conversation` / `F`로 시작합니다. 선택지 문구를 숨은 모드 전환으로 사용하지 않습니다.

`CHARACTER_MEMORY_AVAILABLE=false`로 개인 캐릭터·기억 관리 진입점을 숨깁니다. 관련 구현과 기존 응답 모드는 코드에 남아 있지만, 현재 공개 기능 목록과 구분합니다. 감정 일기·구독도 공개하지 않습니다. 기존 키워드 기반 위기 판정과 고정 안내 UI는 공개 채팅에서 제거했으며, 모델 프롬프트의 기본 안전 경계는 유지합니다.

이전 저장형 `/chat/*` API와 관리자 기능은 운영에서 410으로 차단합니다. 과거 DB 데이터를 자동 삭제하지 않습니다. `NODE_ENV=test`와 `TO_HIGH_ENABLE_LEGACY_TEST_ROUTES=1`을 함께 설정한 테스트에서만 이전 경로를 검증할 수 있습니다. 운영 복구 플래그는 없습니다.

## 대화 생성

```text
사용자 선택 / 직접 입력
  → POST /ephemeral/respond
  → 필요 시 이전 문맥을 일시 요약
  → 레비 답변 스트리밍
  → 답변에 맞는 선택지 생성
  → 브라우저 메모리의 문맥 갱신
```

SSE 요청은 `context`(요약 시), `delta`, `reply`, `options`, `done` 이벤트로 진행하며 JSON 요청도 지원합니다. 답변이 완성된 뒤 선택지를 별도로 생성합니다. 선택지 생성 실패 시 이미 완성한 답변은 기본 선택지와 함께 유지합니다.

입력은 최대 500자이며 요청에는 최대 20메시지와 요약을 포함한 최대 12,000자의 문맥을 허용합니다. 메시지는 사용자·AI 순서로 교대해야 합니다. 요청에 13메시지 이상이 있거나 요약을 포함한 문맥이 8,000자를 넘으면 오래된 대화를 요약하고 최근 5메시지를 유지합니다. 화면의 전체 대화와 다음 요청의 압축 문맥은 별도로 관리합니다.

일반 요청은 답변·선택지 두 번의 모델 생성을 사용하며, 문맥 압축 시 요약 호출이 추가됩니다. 전체 생성은 30초 제한을 공유하고 자동 유료 재시도는 하지 않습니다. 브라우저에는 40초의 별도 응답 제한이 있습니다. 종료·페이지 이동 시 취소 신호를 모델 요청까지 전달합니다.

## 데이터 처리

- 공개 채팅은 Session/UserProfile 저장소를 호출하지 않습니다. 원문과 요약을 DB·localStorage·sessionStorage·IndexedDB·URL에 넣지 않습니다.
- 브라우저에서는 현재 화면의 RAM에만 유지합니다. 종료·새로고침·페이지 이동·BFCache 복원·계정 변경 후 원문을 복구하지 않습니다.
- 서버와 AI 제공자는 답변을 위해 원문과 요약을 처리합니다. 모델 요청의 `store: false`와 제공자 측 보관 정책·ZDR 승인은 별개입니다.
- 비공개 캐릭터 기억 구현은 명시적으로 승인한 정보만 별도 컬렉션에서 관리하며, 상담 원문·전체 요약·세션 ID를 기억으로 저장하지 않습니다.
- 홈페이지의 채널톡·후원 스크립트가 채팅에 남지 않도록 홈과 채팅 사이를 전체 문서로 이동합니다.

## 입력·비용 제한

| 항목 | 현재 코드의 제한 |
| --- | --- |
| 일반 요청 | 사용자 또는 익명 IP 기준 분당 20회 |
| AI 생성 경로 | 합산 분당 10회 |
| 동시 생성 | 계정 또는 익명 IP별 1개 |
| 마지막 사용자 입력 | 500자 |
| 요청 본문 | 64KB |
| 전달 문맥 | 최대 20메시지, 요약 포함 12,000자 |
| 일일 예산 | UTC 기준 프로세스별 요청 수; 실패·중단도 예약 사용량에 포함 |

`TO_HIGH_LLM_DAILY_REQUEST_LIMIT`는 1–100,000 범위의 정수입니다. 개발 기본값은 100이며 운영에서는 명시적으로 설정하지 않으면 생성 요청을 503으로 거절합니다. 카운터는 RAM에 있으며 재시작·다중 인스턴스를 아우르는 통합 비용 한도가 아닙니다.

답변·선택지·요약마다 출력 토큰 상한을 두며, 현재 값과 모델은 [PROMPT_CONFIG](../apps/api/src/prompts/system.ts)에서 관리합니다. 상담 외 직접 작업 요청, 저정보 입력, 반복 입력은 별도 가드에서 처리합니다. 사용자 입력은 비신뢰 데이터로 감싸 시스템 지시와 구분합니다.

이전 저장형 세션의 턴 제한·게스트 소유 토큰 검증은 기존 코드에 남아 있으나, 현재 공개 채팅의 저장 방식이나 인증 요구사항으로 설명하지 않습니다.

## 관측과 운영 확인

브라우저 Sentry 오류·Replay·trace·profile 전송은 비활성화합니다. 서버는 활성화 설정 시 허용된 숫자 지표만 전송합니다. 상담 원문·요약·이름·이메일·IP·임의 오류 본문은 지표에 포함하지 않습니다. 자세한 지표와 전송 필터는 [스트리밍·지표 문서](./chat-streaming-and-metrics.md)에 정리했습니다.

운영 확인 항목은 다중 서버의 통합 비용 관리, AI 제공자 보관 설정, 호스팅·프록시 로그 정책, 인증·환경변수와 Sentry 실제 수신입니다. 로컬 화면·모의 모델 테스트 결과로 이 항목들의 완료를 보장하지 않습니다.

## 로그인과 문의 보호

Google·카카오 로그인은 웹에서 만든 256비트 난수를 같은 탭의 `sessionStorage`에 10분 동안 보관하는 것으로 시작합니다. API는 제공자별 HttpOnly 쿠키(`SameSite=Lax`, 운영에서는 `Secure`)에 같은 `state`를 설정하고 콜백의 `state`와 일치하는지 코드 교환 전에 검사합니다. 콜백에서는 쿠키를 지웁니다. 쿠키가 차단되거나 요청이 일치하지 않으면 로그인을 거절합니다.

로그인 결과의 JWT와 `state`는 URL 쿼리 대신 fragment로 전달합니다. 웹은 저장해 둔 요청의 유효시간과 `state`를 검사하고 한 번만 소비한 뒤 URL을 정리합니다. 시작하지 않은 로그인, 만료된 요청, 재사용된 콜백, 예전 `?token=` 형식은 받아들이지 않습니다. 이 프로토콜 변경은 Web/API를 함께 반영해야 합니다. 전환 중 진행하던 로그인은 다시 시작해야 할 수 있습니다.

문의 생성·추가 요청은 JWT가 있으면 검증해 회원 소유권을 적용하며, 잘못된 JWT를 비회원으로 취급하지 않습니다. JWT가 없는 추가 요청은 `userId`가 없는 문의만 조회합니다. 비회원 문의는 기존처럼 문의 ID를 가진 사람이 이어갈 수 있으므로 ID를 공개하지 않아야 합니다.

운영자 가입 알림은 SMTP 설정이 있을 때만 전송합니다. 프로필 이름·이메일은 HTML 이스케이프하고 이미지는 인증 정보가 포함되지 않은 HTTPS 주소만 허용한 뒤 속성값을 이스케이프합니다. 대화 내용은 포함하지 않습니다.
